# v1.2.1 项目部署引用与真实运行入口

## 评审结论

v1.2.1 在 v1.2 项目生成入口与既有 DeepSeek Harness 可信运行链路之间增加了独立的部署边界。`workflow.project.json` 只保存非敏感的 `deployment_ref`；平台管理员在单独的 `workflow.deployment.json` 中配置运行目录、签名器引用、信任材料路径和凭据环境变量名称。

该设计使业务项目可以使用 `create --deployment-file / deploy-check / run-project` 进入真实执行，同时不把 API Key、HSM PIN、PEM 私钥内容或其他凭据写入项目仓库。

## 为什么不能直接包装原有 run 命令

v1.2 默认 `create` 生成的是供业务评审的未签名软件包。真实 DeepSeek Runner 会强制验证：

- 根签名保护的 Publisher 信任库；
- `registry.lock.json` 分离签名；
- 覆盖 BPMN、Graph、Agent、Policy 和 Lock 的完整软件包清单签名；
- Tool Binding 清单签名与运行时实现摘要；
- 运行事件与检查点的签名策略。

如果只把旧 `run` 命令藏在短命令后面，业务入口会在运行时才发现软件包未签名、密钥未登记或 Tool 没有 Host Binding。v1.2.1 因此先完成签名生成与部署预检，再允许进入 Provider。

## 两类配置的职责

### 项目配置

`workflow.project.json` 由项目团队维护，保存：

- 业务文本、输出目录、Catalog 和总定义；
- Provider、模型和复杂度档位；
- 非敏感部署名称 `deployment_ref`。

项目配置继续拒绝 API Key、PIN、密码、Token、私钥和未知字段。

### 部署配置

`workflow.deployment.json` 由平台管理员维护，保存：

- 与 `deployment_ref` 一致的 `deployment_id`；
- Runtime、Harness Workspace 和 Session 的父目录；
- Cordis、信任库、根签名、公钥、Tool Binding 及其签名的路径；
- Build Signer 与 Runtime Signer 的 PEM 文件路径或 PKCS#11 对象引用；
- DeepSeek API Key 所在环境变量的名称，而不是值；
- 可选的最大 Token 数和不含凭据的 Base URL。

部署配置禁止内联 `api_key`、`pin`、`password`、`private_key`、`secret` 或 `token`。PEM 模式只能引用密钥文件路径；PKCS#11 模式只能引用 Module、Token Label、Key Label、Key ID、Object ID 和 PIN 环境变量名称。

## 命令链路

### 1. 创建受信任软件包

```bash
python scripts/workflowctl.py create \
  examples/readonly-intent-review/workflow.project.json \
  --deployment-file /path/to/workflow.deployment.json
```

正式生成前会验证根信任和 Build Signer 是否以活动状态登记在信任库中。生成结束后再次验证 Registry Lock 与全包清单签名。PKCS#11 Build Signer 缺少 PIN 环境变量时会在写入业务输出前失败。

`--dry-run` 仍保持无外部调用和无项目输出写入。即使提供部署配置，预览也不会调用 PEM 或 HSM 签名器，只报告正式生成计划使用签名。

### 2. 部署预检

```bash
python scripts/workflowctl.py deploy-check \
  examples/readonly-intent-review/workflow.project.json \
  --deployment-file /path/to/workflow.deployment.json
```

该命令检查：

- 项目复核与确定性合同测试；
- Registry Lock 和全包清单签名；
- 根信任与 Tool Binding 签名；
- Build/Runtime Signer 与复杂度档位是否匹配；
- Agent、Tool、完成证据和 Host Binding 是否完整。

增加 `--live` 后，还会检查当前环境是否具有 DeepSeek API Key、官方 SDK、受支持的操作系统和运行 PKCS#11 PIN。报告只返回环境变量名称和“是否存在”，不会返回凭据值。

### 3. 真实运行

```bash
python scripts/workflowctl.py run-project \
  examples/readonly-intent-review/workflow.project.json \
  --deployment-file /path/to/workflow.deployment.json \
  --run-id run-readonly-intent-review
```

运行前会再次执行完整部署预检。没有提供 `--facts` 时，系统把项目业务文本放入 `facts.business.description`；提供 `--facts` 时使用指定 JSON。相同 `run-id` 会遵循现有暂停恢复与检查点规则，而不会重新播放已经完成的节点。

## Tool 证据一致性修复

本增量修复了 v1.2 初版中预检与真实执行之间的一个差异：受控动作“解析并复核业务意图”现在生成 `facts.intent.parsed == true` 完成证据，与 `parse-business-intent` 的真实 Tool 输出一致。

预检同时验证 Tool 是否存在经过审查的 DeepSeek Host Binding。仅存在于 Catalog、但尚未实现 Host Binding 的 `extract-process-entities` 会返回 `BLOCKED`，不能再被误判为 `READY`。

## 复杂度边界

- Dev 可以不签名运行事件，但进入 DeepSeek 真实链路的软件包仍必须经过根信任保护；
- Team 强制 Runtime Signer、SQLite、租约和 90 天默认保留；
- Regulated 继续强制 Runtime Signer、离线根、SQLite、租约和 365 天默认保留；
- PEM 适用于开发和集成测试，金融生产仍建议使用已验收的 PKCS#11 HSM；
- 部署文件可以进入受控配置仓库，但其中引用的密钥文件、PIN 和 API Key 不得进入仓库。

## 自动化验收

本增量覆盖：

- 项目部署引用一致性；
- 内联敏感字段拒绝；
- 部署 Dry Run 不签名、不写输出；
- Build Signer 活动登记与根信任；
- 签名软件包生成与强制验签；
- 部署预检 CLI；
- 缺少真实凭据的可操作错误且不泄漏值；
- Contract Harness 端到端完成；
- Tool 完成证据与 Host Binding 阻塞测试。

真实 DeepSeek Live Test 和真实 HSM Live Test 仍由目标环境执行，自动化 Contract Harness 不能替代外部 Provider 与硬件验收。
