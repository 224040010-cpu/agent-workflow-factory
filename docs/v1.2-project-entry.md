# v1.2 项目配置与一键业务入口设计

## 评审结论

v1.2 第一阶段把过去分散的路径、模型和运行档位收敛为一份可版本化项目定义，并提供 `create / review / test-run` 三个短命令。业务人员可以先看流程图与权限解释，再决定是否进入真实执行；平台与安全参数仍保留在底层受治理运行链路，不向业务入口泄漏。

本阶段完成的是“项目生成与运行前验证”，不是新的分布式调度器，也不是绕过签名和信任链的快捷执行器。对当前适配器不支持的人工审批、系统脚本和定时循环，命令会明确返回 `BLOCKED`。

## 为什么需要项目定义

旧入口要求每次重复填写业务文本、输出目录、能力目录、总定义、Provider、模型和复杂度档位。参数本身没有错，但把平台知识转嫁给业务评审者，容易出现目录选错、环境差异和安全档位静默下降。

`workflow.project.json` 解决三个问题：

- 可重复：同一项目在 Windows、WSL 和 CI 中解析同一组非敏感配置；
- 可评审：输入、输出、Catalog、Provider、模型与档位都进入版本控制；
- 可收敛：普通用户只操作三个短命令，PKCS#11、事件存储与根信任仍由平台管理员负责。

## 项目文件

Schema 位于 [`../schemas/workflow-project.schema.json`](../schemas/workflow-project.schema.json)。所有相对路径都以项目文件所在目录为基准解析。

```json
{
  "$schema": "../../schemas/workflow-project.schema.json",
  "schema_version": "1.0.0",
  "project_id": "readonly-intent-review",
  "source": "business-description.txt",
  "output": "../../build/projects/readonly-intent-review",
  "catalog": "../../fixtures/catalog.snapshot.json",
  "definition": "../../contracts/system-definition.json",
  "runtime": {
    "profile": "dev",
    "adapter": "deepseek",
    "provider": "deepseek-official",
    "model": "deepseek-v4-flash"
  }
}
```

项目文件采用严格字段校验，未知字段会被拒绝。`api_key`、`pin`、`password`、`private_key`、`secret` 和 `token` 等敏感字段禁止写入项目文件；凭据继续通过环境变量、HSM 或部署平台注入。

## 三个短命令

### create

`create --dry-run` 在系统临时目录运行完整的自然语言解释、BPMN 生成和 Graph 编译，返回以下预览后自动删除临时产物：

- 业务名称、目标、解释置信度、警告与假设；
- BPMN、整体 SVG、结构化需求和 Graph 交付物；
- Graph 入口、终点、节点数、边数与动作类型；
- 生成的 Agent、每个 Agent 获得的 Tool 与权限；
- 固定 Tool 的版本、风险级别和治理状态；
- Runtime Policy 与 `dev / team / regulated` 档位解释。

预览明确返回 `external_calls: false`、`writes_to_project_output: false`。正式 `create` 才写入配置的输出目录；如果目录已经包含文件，命令会拒绝隐式覆盖，避免新旧交付物混用。

### review

`review` 复核已经生成的项目，检查：

- `business-view.json` 中列出的每个交付物都存在；
- 每个交付物的 SHA-256 摘要与清单一致；
- Workflow IR、Graph、Registry Lock、Runtime Policy 与编译报告通过软件包校验；
- 业务解释的警告、假设与 `REVIEW_REQUIRED` 状态能够被查看。

该命令不会替业务负责人作出批准决定。`PASS` 只表示交付物完整且结构合法，不表示业务语义已经被人确认。

### test-run

`test-run` 第一阶段采用确定性合同测试，不调用真实模型：

1. 复用 `review` 的软件包与摘要检查；
2. 读取 Runtime Policy 所声明的能力要求；
3. 与 DeepSeek 只读适配器的真实能力进行协商；
4. 检查 Graph 动作是否只包含当前可执行的 `agent_task / tool_task`；
5. 返回 `READY` 或包含具体原因的 `BLOCKED`。

`test-run --dry-run` 允许在尚未生成正式目录时完成同样的预检。它会临时编译项目，整个过程不写项目目录，也不会产生模型费用。

## 受控 Tool 绑定

第一阶段只对少量明确的中文动作进行确定性绑定，例如“解析并复核业务意图”绑定已批准的 `parse-business-intent@1.0.0`。没有命中的 Agent 动作仍能生成 Agent Profile，但不会自动获得 Tool 权限。

这种策略有意避免根据相似词开放式猜测高风险工具。后续如果增加绑定，必须同步完成 Catalog 状态校验、风险策略、输入输出 Schema 与测试；不能只新增关键词。

## 两个验收分支

`examples/readonly-intent-review` 只包含受治理的 Agent 与只读 Tool，合同测试返回 `READY`。

`examples/expense-reimbursement` 包含人工任务和财务系统脚本。当前 DeepSeek 只读适配器没有 `human_gate` 能力，也不执行 `script_task`，因此合同测试返回 `BLOCKED` 并列出两个原因。该结果证明能力协商在真实阻止错误部署，而不是只用于展示。

## 与真实运行的边界

`test-run` 不会读取 DeepSeek API Key，也不会建立 Harness 会话。真实 DeepSeek、受根保护的软件包、运行签名、SQLite 事件、租约和 HSM 仍使用已有 `run` 命令与 v1.1 验收链路。

下一增量将设计“项目级部署引用”，只引用部署环境中已经登记的信任材料和运行策略，不把私钥、PIN 或凭据写回项目文件。完成后，短命令才能安全地连接真实 Provider。

## 测试与退出标准

第一阶段必须通过：

- 项目 Schema、相对路径、未知字段和敏感字段测试；
- `create --dry-run` 无正式目录写入和无外部调用测试；
- 受控 Agent/Tool 绑定与 Runtime Policy 展示测试；
- 正式生成、复核和交付物篡改拒绝测试；
- `READY / BLOCKED` 两类能力协商测试；
- CLI JSON 报告、Windows 和 WSL 全量回归。

本阶段不声称完成的能力包括真实 Provider 一键执行、人工审批适配器、系统任务执行器、定时循环、跨主机调度与可视化控制面。
