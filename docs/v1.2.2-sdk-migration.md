# v1.2.2：DeepSeek Harness SDK 迁移与验收

更新日期：2026-10-03。状态：兼容代码与本地合同验证完成，目标环境真实 API 验收待完成。

## 本轮升级了什么

本轮是 Desktop 集成的前置兼容层，不是 Desktop 插件发布。Factory 继续掌握 BPMN、Graph、Registry Lock、信任链、检查点和运行状态；不读写个人 Desktop Profile，也不依赖桌面私有接口。

- SDK 和原生 Runtime 都精确固定为 `0.1.5rc1`，拒绝版本不匹配。
- `session_root / cordis` 改为 `dsh_home / profile / patches`。
- 只允许 `sdk-minimal`、一个固定摘要的只读 Patch 和独立 Home。
- 禁用 Bash、Pwsh、对应终端插件；关闭 Session Log 上传及插件清单附加。
- 禁止 Home/Profile 中的非空额外配置、额外 Bundle/依赖和 `.env`；拒绝 `NODE_OPTIONS / NODE_PATH` 注入。
- 记录 SDK/Runtime 版本、平台、Profile、Patch 摘要、Provider、Model 和 Home 路径摘要。
- 缺失或变化的运行来源不能继续旧 run-id；不接受缺失 Finish Reason 的结果。
- 兼容新版嵌套 `assistant/message` Usage；继续保留结构化错误脱敏。
- 增加 Windows/Linux CI 合同测试，不要求真实模型凭据。

双仓共享总定义和 Skill Registry 的职责边界未改变，不需要为这次 Runtime 兼容迁移修改能力语义。

## 实测发现：恢复工作流不等于恢复旧对话

固定版本 JSON-RPC 服务只暴露 initialize、session/prompt 和 shutdown，没有跨进程 session/load。重启进程后直接使用已持久化的 session_id，会返回 `session already exists`。

因此本适配器明确采用以下语义：

1. 同一客户端实例内，相同逻辑会话仍复用同一 Harness 会话。
2. 关闭、重启后，由 Factory 验证并加载签名检查点；已完成节点不重跑。
3. 未完成节点使用新的实际 Harness 会话，重新发送完整的当前 Facts、Agent 职责和工具证据。
4. 逻辑 ID 与实际 ID 都记录在 `agent.turn.completed`，旧会话日志不删除。

这保留了当前“只读、幂等、完整证据提示”的工作流恢复能力，但**不恢复模型旧对话历史，不承诺任意有状态 Agent 的跨进程连续对话**。尚未开放的写操作和非幂等 Tool 不能套用此策略。中断节点可能再次消耗 Token，重试仍计入原运行预算。

## 升级前准备

使用 Python 3.11+，先完成或暂停旧运行，保留旧虚拟环境、Runtime 目录、信任材料和会话日志。不要覆盖已有构建目录，也不要删除个人 `~/.dsh`。

在已取得本轮代码的仓库根目录中，建议新建虚拟环境：

### WSL / Linux

```bash
python3 -m venv .venv-v122
source .venv-v122/bin/activate
python -m pip install -e '.[deepseek]'
```

### Windows PowerShell

```powershell
py -3.12 -m venv .venv-v122
.\.venv-v122\Scripts\Activate.ps1
python -m pip install -e '.[deepseek]'
```

PKCS#11 用户把安装项改为 `'.[deepseek,pkcs11]'`。Windows SDK 可用不代表 Windows 已安装 SoftHSM；既有 WSL PKCS#11 环境仍需单独验收。

检查版本（不会显示凭据）：

```bash
python -c "import workflow_factory; from importlib.metadata import version; print(workflow_factory.__version__); print(version('deepseek-harness-sdk')); print(version('deepseek-harness-runtime-bin'))"
```

应依次显示 `1.2.2 / 0.1.5rc1 / 0.1.5rc1`。

## 迁移部署配置

复制新版 `examples/readonly-intent-review/workflow.deployment.example.json` 到新的本地部署文件，不要覆盖旧配置；保留原部署名称、可信公钥、签名器引用和凭据环境变量名。

关键字段示例（是片段，不是完整配置）：

```json
{
  "schema_version": "1.1.0",
  "runtime_dir": "/home/dell/awf-runtime-v122",
  "dsh_home": "/home/dell/awf-runtime-v122/harness-home",
  "harness_profile": "sdk-minimal",
  "patches": ["/home/dell/src/agent-workflow-factory/adapters/deepseek-harness/readonly.patch.yml"]
}
```

请替换为本机路径。Windows 可使用 `C:/work/...`。相对路径以部署文件目录解析。删除旧 `cordis` 字段；不要复用 Desktop Home。SDK 会在独立 Home 中生成默认 Profile，不要手工安装插件或修改生成配置。

原始 `run` CLI 默认创建 `<runtime-dir>/harness-home-v122`；自定义只读 Patch 的参数名是 `--harness-patch`，但其内容仍必须匹配受审查摘要。不要再传 `--cordis`。

## 分层验收

### 1. 基础离线回归

```bash
python -m unittest discover -s tests -v
```

不设置 Live 开关时，真实 API、PKCS#11 环境测试和可选官方 Runtime 测试会跳过。`OK (skipped=...)` 只证明已执行部分通过。

### 2. 官方 SDK + 本地假模型

此层启动真实 SDK 和原生运行包，但模型服务由 localhost 测试服务器提供；使用测试假 Key，不读取真实 Key 调用付费模型。

WSL：

```bash
AWF_SDK_RUNTIME_TEST=1 python -m unittest discover -s tests -v
```

PowerShell：

```powershell
$env:AWF_SDK_RUNTIME_TEST = '1'
python -m unittest discover -s tests -v
Remove-Item Env:AWF_SDK_RUNTIME_TEST
```

该层检查最终 Profile、模型请求不含 Tool、同进程后续轮次、跨进程新会话，以及“两个 Agent—第二节点中断—新进程恢复—第一节点不重跑—签名重放”的综合链路。它不能证明真实模型理解能力或真实 API 的可用性。

Windows Runtime 首次启动可能需要写入用户 `.cache/pkg` 解包缓存；受限环境需允许对应缓存目录，而不是修改项目安全策略。

### 3. 真实 DeepSeek API

在已安全设置 `DEEPSEEK_API_KEY` 的终端中执行。下面的测试会产生模型调用费用，不应放入普通 CI：

```bash
DSH_LIVE_TEST=1 DSH_MULTINODE_LIVE_TEST=1 python -m unittest discover -s tests -p 'test_deepseek_harness.py' -v
```

PowerShell 分别设置 `$env:DSH_LIVE_TEST = '1'` 和 `$env:DSH_MULTINODE_LIVE_TEST = '1'` 后，运行同一条 Python 命令；结束后移除两个环境变量。

必须确认 `test_official_sdk_smoke` 和 `test_official_sdk_runs_two_agent_graph` 都显示 `ok` 而不是 `skipped`。不要截图或发送 API Key。

### 4. 持久化部署与 HSM 验收

按 README 的 `create --deployment-file → deploy-check --live → run-project → runtime-replay` 顺序，使用新版部署文件和新的 `--run-id`。再执行原有篡改拒绝与 PKCS#11 验收。旧运行仅用于历史重放，不允许跨 SDK 配置继续执行。

## 当前验证记录与已知限制

本轮在 Windows x64 / Python 3.12 上运行完整测试集，包括官方 Runtime 的 localhost 集成测试。真实 DeepSeek API 与实际 PKCS#11 Token 未在本轮调用；WSL 和云端 CI 尚未在本轮执行。历史 v1.1 验收不自动视作本版本验收。

最终本地结果：`Ran 108 tests / OK (skipped=3)`，即 105 项通过、3 项外部环境相关测试跳过。额外检查：项目可编辑安装成功、`pip check` 通过、总定义校验通过、`test-run --dry-run` 返回 `PASS / READY`、Python 编译检查和 `git diff --check` 通过。Windows CLI 子进程测试已明确使用 UTF-8，避免父子进程编码不一致导致中文 JSON 解码失败。

三个跳过项分别是真实 DeepSeek 单节点测试、真实 DeepSeek 多节点测试和真实 PKCS#11 Token 测试；它们需要在目标环境显式打开对应开关，不能把跳过误报为通过。

官方 SDK 关闭时仍可能报告 `ResourceWarning: unclosed file`（stdout/stderr 管道）；本轮成功用例也复现此上游警告。适配器调用公开 `close()`，未通过访问私有进程字段打补丁，也未屏蔽警告。需与真实 `ERROR/FAILED` 区分，长驻服务发布前应进一步验证资源释放。

Patch 不构成 OS 沙箱，部署 Home、安装包和宿主代码仍须置于可信访问控制下；对本机管理员篡改或进程级网络访问没有额外隔离保证。需要强隔离时应使用独立服务账户/容器及外部网络策略。

下一步先完成目标 WSL 环境的 Live 验收，再开发 v1.3 的 `desktop-export`，最后接入 Desktop 插件和人工评审，不同时铺开企业 Web 平台。
